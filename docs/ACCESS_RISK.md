# Vyper Guard Access Risk

Vyper Guard Access Risk is an offline-first rules engine for reviewing SaaS identities, permissions, grants, activity, and log coverage. It produces evidence-linked review findings and a dry-run remediation plan. It does not integrate directly with a SaaS provider or change access.

## Architecture and input

`guardian.access_risk` contains typed provider-neutral schema declarations, JSON validation, deterministic rules, capped risk scoring, dry-run planning, explanation adapters, and report rendering. The CLI is registered as `vyper-guard access-risk` in the existing Typer application. A JSON snapshot has `as_of`, optional `policy`, and arrays for `identities`, `permissions`, `grants`, `events`, `assets`, and `log_coverage`. Timestamps must be timezone-aware ISO-8601 values. Grant and event references are checked. See `examples/access_risk_demo.json` for a complete fixture.

The input hash is SHA-256 over canonicalized parsed JSON plus the names and SHA-256 digests of linked contract-report files (unavailable reports are represented with a null digest). Finding IDs are stable hashes of rule, identity, and permission IDs; timestamps are excluded. Findings sort by priority and then severity and ID. A supplied fixed `--as-of` makes output reproducible.

## Rules

Thresholds can be overridden by the input `policy` object or `--policy` YAML/JSON file. Defaults are:

| Rule | Default and evidence | Output |
|---|---|---|
| R1 `stale_identity` | Disabled/terminated identity with active grant; active/inactive identity activity older than 45 days | CRITICAL for sensitive/deploy/admin disabled access, otherwise HIGH; old active identity HIGH if sensitive, otherwise MEDIUM |
| R2 `unused_permission` | Grant at least 60 days old, no matching successful event, and declared application/event coverage spanning the complete 60-day window | Severity follows permission risk. Missing event-type or window coverage produces INFO `insufficient_evidence`; it never asserts unused access |
| R3 `excessive_scope` | Configurable broad tokens (`*`, `admin`, `owner`, `delete-all`, `write-all`, `domain-wide`) or external sharing | CRITICAL for broad+sensitive+external, HIGH for broad+sensitive, MEDIUM for broad, LOW for external sharing alone |
| R4 `peer_drift` | Team/role group of at least 4; permission held by at most 20% of peers and sensitive or above the group's common risk level | MEDIUM, or HIGH for sensitive/deploy/admin. Wording calls this an exception requiring confirmation, not misconduct. Smaller groups emit INFO evidence-gap notes. At exactly four peers a permission held by one person is 25%, so the default 20% rarity cutoff cannot flag it. |
| R5 `unusual_activity` | At least 10 baseline events in the prior 60-day window excluding the recent 14 days; flags new country, application, resource, or first privileged use | One finding per user/day cluster; new country MEDIUM; new country plus first privileged use HIGH. Missing baseline emits INFO evidence-gap note. |
| R6 `cross_layer_exposure` | `deploy`/`admin` permission tied to a smart-contract asset whose linked Vyper report contains a verified access-control-family detector at MEDIUM+ | HIGH, or CRITICAL for a HIGH/CRITICAL contract finding when the identity has another SaaS finding. Raises priority separately; it does not change the existing SaaS finding severity. |

The verified access-control family is configurable and defaults to `unprotected_state_change`, `tx_origin_auth`, `unprotected_selfdestruct`, and `dangerous_delegatecall`. The sample report was generated by the current Vyper Guard CLI and contains verified HIGH and CRITICAL matches.

## Scoring and remediation

The clearly labeled **Access Risk Score (higher = more risk)** uses per-finding weights CRITICAL 30, HIGH 20, MEDIUM 10, LOW 5, INFO 1. Per identity, points cap per band at 50/40/20/10/5 and the total caps at 100. Organization score is `min(100, round(0.6 * max_identity + 0.4 * mean_identity))`. Risk grades are A=0–19, B=20–39, C=40–59, D=60–79, F=80–100; they are not certifications.

T1 is a policy flag for a narrowly scoped, high-confidence revocation candidate; T2 requires manager/app-owner review; T3 is advisory or evidence-limited. The included `DryRunExecutor` only emits `{action,target,tier,approver_required,rollback_note}`. No execute option or real remediation client exists. `auto_revocation_allowed` is a flag, not an action.

The report disclaimer is: “This score reflects detected access risk from the supplied evidence only. It does not certify that an organization is secure.”

## Explanations and reports

Template explanations work offline and are deterministic. Optional `--explain bedrock` uses a lazy Bedrock Converse client if credentials and `GUARDIAN_BEDROCK_MODEL_ID` are available; output schema failures, unknown evidence references, missing configuration, and service errors fall back to the template. Explanations can only paraphrase evidence; the rules engine remains the sole source of findings and grades.

CLI, JSON, Markdown, and single-file HTML output include findings/evidence, org and identity scores, dry-run plan, correlation wording, limitations, and disclaimer. HTML embeds its CSS and includes a before/projected view. The projection removes T1 candidates from a copied input and reruns the rules; it never changes source data or a SaaS system.

## Limitations

- Results are only as complete as supplied identities, grants, event telemetry, and coverage declarations.
- Peer comparison, broad-token matching, and anomaly rules are heuristics requiring human confirmation.
- A Vyper Guard detector match is a static-analysis signal, not proof a contract is exploitable.
- A missing or invalid contract report is reported as an evidence gap and does not disable SaaS analysis.
- Inputs and demo data are synthetic; these rules have not been measured against production access-review outcomes.
- AWS deployment, permissions, Bedrock account access, and cost behavior were not verified in an AWS account.

## What is deliberately not built

Every SaaS vendor's connector; replacing an identity provider; automatic revocation without approval; compliance certification; a multi-tenant control plane; AI as a source of truth; complete insider-threat detection; live AWS deployment; or production accuracy claims.

AWS AppFlow for supported SaaS data sources, Security Hub custom findings, and IAM Access Analyzer output are possible future input extensions. IAM Access Analyzer would cover AWS IAM only, not other SaaS applications. None is integrated here.
